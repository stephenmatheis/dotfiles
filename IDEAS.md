# Ideas

Plans and ideas for these dotfiles, mostly the hax0r themes. Started 2026-10-30. Items marked *unverified* are from memory or a guess and need checking on a machine before anyone builds on them.

## Where things stand (2026-11-21)

Memory is per machine, so a fresh session on the other Mac won't know any of this. Read this file and the README first.

- **15 themes.** The original six (`green`, `red`, `blue`, `amber`, `white`, `black`), the single-color `pink`, `purple` and `electric`, the dual `cyan-pink` and `pink-cyan`, and four full-color copies of other themes: `dark-modern`, `light-modern`, `merino-light` and `merino-dark` (see Full-color themes).
- **Every switch reaches** Ghostty, tmux, nvim, fzf, lazygit and Claude Code. **Opt-in per machine:** `macos`, `shader`, `rex`, `vscode`, `xcode`, `chrome`, `delta` and `raycast`. `hax0r status` shows which are on.
- **On `steve-mbp-16-m2-max`:** everything but `shader` and `chrome` is on.
- **The other Mac still needs:** `chezmoi update`, `hax0r vscode on` (VS Code stops following the theme until it's run), the `~/.zshenv` lines for fzf and lazygit, the neoclear build, and whichever other opt-ins it should have. *Unverified:* not checked on that Mac since early November.
- **Mock-ups:** `page.lua` for the one- and two-color themes, `page-full.lua` for the full-color ones:

  ```zsh
  nvim -l ~/.config/hax0r/page.lua page.html && open page.html
  nvim -l ~/.config/hax0r/page-full.lua page.html dark-modern && open page.html
  ```

## Decided

- **Name: on hold, so everything is still `hax0r`.** `phosphor` was the first pick (2026-10-30), but since the full-color themes it no longer fits every theme. Candidates as of 2026-11-21, checked against Homebrew, npm, the PATH on `steve-mbp-16-m2-max` and a web search (not every registry, and no trademark search):
  - **`phos`**, the front-runner. It keeps the CRT story without spelling it out: real phosphors came in green, amber, white and the red, green and blue of color tubes, so the one- and two-color themes all fit. Read it as "the glow on the screen" for the full-color ones. Said "foss". Its only clash is a small Rust log colorizer on Arch's AUR, not in Homebrew.
  - **`fsfr`**, "phosphor" without the vowels. Free everywhere checked, but it reads as FSF or FSFE (the Free Software Foundation) and "fs" suggests "filesystem", and it isn't obvious how to say it.
  - **`lnf`**, for look and feel. Free in Homebrew and on this Mac, and the npm name is a small symlink tool. Close to `ln` and `lf` (a popular terminal file manager), so it's easy to mistype or misread.
  - Ruled out: `livery` (fits, but sounds picked by an AI), `tinct` (an active theme tool doing the same job), `tint` (crowded: a Homebrew color picker, Go's `tint` logger, an old theme switcher), `lume` (a well-known Homebrew VM tool), `glow` (a popular Charm CLI), `neon` (doesn't fit amber, white or black). `crt` is short and was considered. Similar tools to know about: tinty, lumos and teems.
  - When it happens: rename before generating more themes, as its own commit. The "HaX0R Gr33N / R3D / BLUE" titles stay: they're credited to the original iTerm themes.
  - Scope, counted 2026-11-21: about 545 mentions in 28 hand-written files (the `hax0r` script has 190, `generate.lua` 59, the manual 33, the README 32), plus about 150 generated files with `hax0r` in their names, which `hax0r build` writes again. Also VS Code theme and icon ids, `colors/hax0r.lua`, Ghostty and tmux theme files, and `~/.config/hax0r`.
  - Per-machine state needs a one-time migration on each machine: `~/.local/state/hax0r`, `~/.claude/themes/hax0r.json` and `custom:hax0r` in `~/.claude/settings.json`, VS Code's `workbench.colorTheme` / `workbench.iconTheme`, and the `hax0r-*` custom themes in Rex (re-imported under the new name by `rex apply`; delete the old ones in Rex's Settings ▸ Themes). Retire old paths with `.chezmoiremove`, as before.
  - Two things outside the repo also point at the old name: the `~/.zshrc` line that sources `vscode/hax0r-theme/terminal-palette.zsh`, and VS Code's extension registry (`~/.vscode/extensions/extensions.json`, id `stephenmatheis.hax0r-theme`, location `~/.config/vscode/hax0r-theme`). Option: keep that one folder and id, which is never typed, so neither needs a manual edit. The `~/.zshenv` lines for fzf and lazygit, the `clear` alias in `~/.zshrc`, and the other Mac's opt-ins need checking too.
- **Dual themes may break "a theme stays one color".** The second hue takes the jobs brightness handles worst: removed lines, errors, links and Claude Code's `*Shimmer` keys.
- **Preview first:** add options to `page.lua` and look before editing `palettes.lua`.
- **Picked (2026-10-30), all matched to Gr33N's contrast** (the other way, matching only its lightness, was more vivid but dimmer to read and had more colors that clash, so it was dropped): `pink` (OKLCH hue 355), `purple` (300), `electric` (electric blue, 258; `blue` is taken), and the dual themes `cyan-pink` (cyan 195 with pink as the second color) and `pink-cyan` (the reverse). Purple + amber, green + amber and blue + orange weren't picked yet.

## New monochrome themes

Neon pink, electric blue and purple.

- Purple and electric blue are dark at full saturation, so they have to be lifted to match Gr33N's readability (red was lifted the same way).
- The existing blue (`#11b7ff`) is a sky blue, so a new blue needs a distinct hue.
- Approach: an OKLCH helper in `palettes.lua` that builds a whole theme from a hue by rotating Gr33N's colors (same lightness and relative saturation per role). Check it by regenerating Gr33N from itself, which should give the same colors, and amber, which was matched by hand.
- Starting hues in OKLCH degrees (*unverified*, judge on the page): pink 325 to 355, purple 290 to 310, electric blue 250 to 266, existing blue about 235.
- Show contrast ratios on the page, so nothing falls short the way red did (2.76:1).

## Dual themes

Two hues that go together, with equal OKLCH lightness so neither dominates. The accent takes removed, error, link and the shimmer; the primary keeps everything else.

- cyan + pink (the cyberpunk one; the accent is the warm color so errors read as errors)
- purple + amber
- green + amber (colors that already exist, a two-tone phosphor look)
- blue + orange (teal and orange)

- **Syntax colors: comments take the accent (2026-10-30), picked from the page.** Strings, functions and constants would match links and sit 1.18:1 from errors, and types and keywords the reverse, which is why they stayed in the first hue. Comments show the accent in nvim and VS Code; Claude Code's code blocks read ANSI 8, so their comments keep the theme's dim color.

- **Starship and git: no change (2026-10-30), picked from the page.** If they come back, don't remap ANSI colors, which changes every terminal tool. Two new palette slots work: 197 and 198 were built and then removed, the second hue and its dim shade in a dual theme and `normal` and `dim` in the rest, which match ANSI 1, 2 and 6 and ANSI 8 in every theme, so the single-color themes don't change. Each Ghostty theme and `terminal-palette.zsh` would set them, Starship's styles can name them, and git's config too (`color.diff.old = 197 dim`, `color.status.changed` and `untracked`), which keeps it to git alone. Terminals that don't set the slots would show their standard pinks.

## Full-color themes

Exact copies of other themes, applied to every app the way hax0r does it. A theme with a `syntax` table is full color: nvim gets finer syntax groups, Xcode gets kinds and delta gets syntax highlighting. VS Code uses each theme's own template in `vscode/hax0r-theme/themes/`, made from the source theme's files by a one-off script so every color matches. The one- and two-color themes are unchanged.

- **`dark-modern`** and **`light-modern`** (2026-11-05): VS Code's Dark Modern and Light Modern. Terminal colors are darkened the way VS Code's terminal draws them (its 4.5:1 minimum contrast), since Ghostty and nvim draw colors as stored. Light Modern keeps Light+'s code colors.
- **`merino-light`** and **`merino-dark`** (2026-11-06): Rex's Merino terminal colors, which are GitHub's Primer colors, with code and editor colors from GitHub's VS Code theme (MIT). Rex gets hax0r's copies rather than its built-in Merino, because only hax0r's files set the terminal slots Claude Code draws its diff bands in (22, 28, 52 and 88).
- **Settled:** Claude Code's code-block colors can't match nvim's or VS Code's. It gives each kind of code a fixed terminal slot (keywords 4, strings 1, functions 3, comments 2), and changing those slots would recolor every program.

## Animations

- **Claude Code shimmer:** second hue in the dual themes (2026-10-30), set in `theme()` in `palettes.lua`. A theme only sets the color, and Claude Code decides when it animates. Read from 2.1.314's minified code: the spinner sweeps a 3-character band of plain shimmer color while requesting and responding, and the whole message pulses on a 2-second cycle during tool use, blending only colors it can parse as `rgb(r,g,b)` (our theme files use hex). Hooks use `claudeBlueShimmer_FOR_SYSTEM_SPINNER`, and typing `ultrathink` uses the `rainbow_*_shimmer` keys. No use found for `promptBorderShimmer`, `permissionShimmer`, `inactiveShimmer`, `warningShimmer` or `fastModeShimmer`, so the border and permission rows on the page probably show animations that never happen. *Unverified:* how the tool-use pulse looks with these colors, and whether a stalled spinner, which moves toward the error color, still stands out now that the sweep uses the second hue too. If it's too loud, the hook spinner alone is the quieter option.
- **neoclear** (https://codeberg.org/ftranschel/neoclear/): a `clear` replacement that pours braille glyph streams down the screen, cmatrix-style. Rust, standard library only (a little libc), GPL-3.0 or later. Options for direction (`-d`), duration (`-t`) and color (`-c`), speed, trail length and glitch rate; defaults go in `~/.config/neoclear/config.toml` via `--write-config`. Prints a plain clear when output isn't a terminal.
  - **Linux only upstream:** `src/main.rs` has a `compile_error!` for anything else, and `src/term.rs` uses Linux values. Read on 2026-10-30, it has no dependencies or build script, and it only prints escape codes and reads its config. The patch is small: allow macOS in the `compile_error!` check, use `TIOCGWINSZ` 0x40087468 on macOS, set `LFLAG_OFFSET` to 24 on macOS, clear `ICANON` along with `ECHO` so Ghostty doesn't show its password-prompt lock cursor, and add `--hold-sync` so the prompt closes the final synchronized update and appears in the same frame as the clear. It's backed up on the `macos` branch of the private repo `stephenmatheis/neoclear` (a SHA-1 export, since upstream's SHA-256 repo can't be pushed to GitHub; the README has the steps), and it's built and installed to `~/.local/bin` on `steve-mbp-16-m2-max` and passing checks in a simulated terminal. The other Mac still needs it (README, new-machine checklist). Don't copy its source into this repo (the license).
  - Wrapper: `hax0r clear` passes the current theme's foreground as `--color` and falls back to plain `clear` without neoclear. Fades go to black, not the theme's background, and the head glyph tints toward white, so check `black` (white background) by eye.
  - The alias (`alias clear="hax0r clear --hold-sync"`) and the `PROMPT+=` line that closes the update are in `~/.zshrc`, which isn't tracked, so they're on the README's new-machine checklist. `~/.config/neoclear/config.toml` sets `fade_ms = 0`.
- **Theme-switch fade:** built (2026-10-30). `hax0r <theme>` holds the terminal at the old colors with OSC 10/11 escape codes, signals every app at once, fades, then resets with OSC 110/111. It only fades the Ghostty terminal that ran it, and not under tmux; the others get the normal reload. ANSI colors change at the reload, as the fade starts. Each app and wallpaper still starts on its own reload time: macOS is the slowest, about half a second in, because `WallpaperAgent` has to restart. Tried in Ghostty after the reorder (2026-10-30): a bit faster, and good enough for now. Holding everything back to match the wallpaper would slow every switch, so it wasn't done.
- **Ghostty shader:** built (2026-10-31), picked from a live preview page: scanlines at 0.50 and glow at 0.65, opt-in per machine with `hax0r shader on`. The README has the details. Flicker was dropped: at 0.02 it couldn't be seen, and it would have needed the animation loop, which Ghostty puts at generally under 10% more CPU. Tried in Ghostty 1.4.0 in test windows: it compiles, turning it on and off reaches a running window, and with the background changed by escape codes, as the switch fade does, the background stays within one color step of the theme's. A real `hax0r <theme>` fade with the shader on works (2026-10-31): still a little choppy, with each window and app starting and ending at its own pace, and everything settled within 2 to 3 seconds. Accepted for now. *Unverified:* how it feels over a day of use.
- **nvim:** a cursor-smear plugin would work (`vim.pack` is already in use). Low priority.

## Where else to apply the theme

Tools that use the ANSI palette already follow Ghostty. The ones that need hex colors:

- `fzf`: built (2026-10-31), picked from the page: matches in `link`, which is the second hue in the dual themes, on a `cursor_line` band. It uses `FZF_DEFAULT_OPTS_FILE`, so no shell has to re-read anything. Checked in Ghostty by eye in `black` and `pink-cyan` (2026-10-31). The README has the details. Shell key bindings (Ctrl-R and so on) aren't set up in `~/.zshrc`, so this shows only when `fzf` is run directly. The other Mac still needs the `~/.zshenv` line (README, new-machine checklist).
- Xcode: built (2026-10-31), `hax0r xcode on`, opt-in per machine, through an unofficial workaround the user asked for after the official routes ran out: the README and the comment above `xcode_apply` in `hax0r` have the details. Tested on Xcode 27.2: a running Xcode reloads the selected theme's file within a few seconds, the background comes out at or within one step of the theme's in `green`, `black`, `white`, `pink` and `red`, and quitting and relaunching keeps the file. Confirmed by eye with a real `hax0r green` from a `hax0r` selection (2026-10-31): Xcode followed by itself, the name stayed `hax0r`, and its settings showed the theme's exact `#19e20e` and `#020f01`. `hax0r black` then took it across to Light the same way, with `#000000` and `#ffffff`. The official route, kept in git history, was a classic `.xccolortheme` per theme imported in Settings ▸ Appearance: Xcode reads those as Generic RGB (gamma 1.8), so colors need converting and some can't land exactly. Also found: changing Xcode's `DVTWorkspaceThemeSettings` preference to a saved theme's ID switches a running Xcode too, which wasn't needed. *Unverified:* the file surviving an Xcode update.
- Chrome: built (2026-10-31), `hax0r chrome on`, opt-in per machine, official routes only, picked from the page and in real Chrome: Faint toolbar, so the toolbar and active tab are `border`, the tab strip is `bg`, and inactive tabs' text is `dim`. Faint tab strip and then Band toolbar were built first and replaced once the user saw them in Chrome; `prompt_band` on the toolbar was too loud. The address bar seems to ignore `omnibox_background`: in screenshots it measured about 10% toward white from the toolbar in all four tries (`#1d2b1d` on `#020f01` with `selection_tint` set, then `#204d1e` on `#073804`, `#1d3b1b` on `#052703` and `#52201f` on `#3c0303` with `bg` set). That's inferred from those colors, not from Chromium's source. Each switch takes a restart or Load unpacked, both confirmed by eye on Chrome 156: `hax0r red` left a running Chrome alone, and a restart then showed red. The README has the details. A tinted active tab on a flat toolbar was tried with a `theme_toolbar` image, whose top row sits about 16 points above the window: 56 rows reach the toolbar but the tab's flares end in mid-air, and 47 rows stop above them but leave a flat bottom. *Unverified:* full screen, and themes other than `green` and `red` in real Chrome, including the light themes `black` and `white`, whose address bar hasn't been measured. `--load-extension` (removed from branded builds) and the `BrowserThemeColor` policy (admin-level, one color) were ruled out by reading Chromium's source.
- Raycast: built (2026-10-31), `hax0r raycast`, official route only, picked from the page and in Theme Studio: Flat, one color. The link format was read from Raycast 2.10's code. `hax0r test` in `green`, with these same colors, installed and showed in Theme Studio by eye, and installing didn't apply it. In Raycast's main window it read well to the user with `fg` text. Measured from screenshots, the window is `#3a3f39` over `green`'s wallpaper and `#424742` over white, not the `#020f01` the theme sets, so about 3% of the wallpaper shows through and something else lightens it, cause not found. That puts `fg` at 3.72:1 and 3.28:1, not the palette's 6.84:1. Extension icons keep their own artwork. When all 11 links opened at once, only the last one installed, so a newer link does replace one still waiting. A scripted switch would be unofficial: the settings databases are encrypted and weren't opened, and `defaults` only holds a theme ID, so that was left alone. *Unverified:* where the accent shows, `hax0r raycast` going through all 11 for real (only a dry run so far), themes other than `green` in Raycast, including how low `red` lands, the light theme `black` with Raycast's Appearance setting, and the themes syncing to the other Mac.
- VS Code: the hax0r extension in `~/.config/vscode/hax0r-theme`, with color and file icon themes for every theme. Opt-in per machine since 2026-11-03 with `hax0r vscode on`, which needs the extension installed from its folder with Developer: Install Extension from Location…. A running VS Code applies a switch at once.
- Rex: built (2026-11-06), `hax0r rex on`, opt-in per machine, official client actions only: each switch imports the theme's Ghostty file and changes to it, which also sets Rex's Light/Dark. Needs the Rex app open: the server runs without it, so a switch while the app is closed skips Rex. `hax0r rex apply` (2026-11-21) catches up. A launch hook was looked into and dropped: `init.lua` never gets events, and the only official trigger is `client_joined` heard by a `rex do --all` script, which would need an always-on LaunchAgent. Rex has no command for Auto, so after `off` that's a hand step.
- Slack: theme files or pasteable theme strings
- `lazygit`: built (2026-10-31), picked from the page: a `cursor_line` band, unstaged files in `white`, `bright` frames with the others `dim`. lazygit's default band is ANSI blue, which hax0r makes the same color as the text on it. Tested on lazygit 0.66.2 by reading what it sends the terminal: all 11 themes draw their colors, and a running lazygit picks up a changed file when focus returns, directly and under tmux with `tmux.conf`'s settings. Checked in Ghostty and tmux by eye in `black`, `green` and `pink-cyan` (2026-10-31). The search border was checked by eye in `pink-cyan`. A copied commit's hash is `link` on `prompt_band`, picked from the page after the first colors proved hard to read with the cursor on it. Both Macs need the `~/.zshenv` line (README, new-machine checklist).
- `delta`: built (2026-10-31), `hax0r delta on`, opt-in per machine, picked from the page: Bands and words, the same bands as Claude Code, no line numbers, no syntax highlighting. Tested on delta 0.20.1 by reading its output: colors match the theme file, and `--color-only` keeps `git add -p`'s line counts. lazygit 0.66.2 never called a stand-in pager set in `core.pager`, so its diffs stay plain. *Unverified:* how it looks by eye across themes, and real use of `git add -p`.
- `bat`, `eza`, `btop` if installed (not yet)

## macOS

**Built (2026-10-30), picked from the page:** `hax0r macos on` sets Light/Dark and a solid wallpaper, opt-in per machine; the README has the details. The accent and highlight stayed out, as below. The wallpaper goes on every Space and display through an unofficial workaround, which edits macOS's undocumented wallpaper store. Official routes were tried first with two Spaces: `NSWorkspace`, System Events, and the Shortcuts action Set Wallpaper Photo, even signed with its hidden `showOnAllSpaces` on. Each reaches every Space only once, then only the current one. The comment above `wallpaper_set` in `hax0r` has the details. Retry them after macOS updates, and delete the workaround if one works. The workaround was tested with two displays, and with two Spaces on one display by reading the store. *Unverified:* moving between several Spaces by eye.

Checked on one machine on 2026-10-30: macOS 27.0.1, light mode, default accent (no appearance keys set). Confirm each remaining option on the machine before wiring it in.

- **Official, in System Settings:** accent color (a fixed set, so the nearest match) and highlight color (custom). Accessibility ▸ Display ▸ Color Filters has a color tint, which gives a full-screen phosphor effect.
- **Second, not a documented API:** writing `AppleAccentColor` and `AppleHighlightColor` with `defaults write -g`, which is what the UI writes.
